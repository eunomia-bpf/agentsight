  ---
  AgentProf 核心算法

  问题：为什么 AI Agent 需要新的 Profiling 方法？

  传统 CPU profiler（pprof、flamegraph）靠 调用栈 做归因：malloc 的成本同时算到
  parse、process、main 上。但 Agent 轨迹有两个结构性缺失：

  1. 没有稳定语义身份 — 自然语言 prompt 表达同一意图可以用不同文字，没法直接折叠
  2. 没有运行时调用层次 — 一串 prompt
  可能是一个任务也可能是多个，没有机制标记边界

  核心模型：Semantic Operation Stack

  设计目标（D1-D3）：
  - D1：守恒多资源度量（token、time、file effects 等，重新分组不改变总量）
  - D2：共享语义身份（跨 session 的相同责任用同一个短名字）
  - D3：层次但不丢 evidence（保留 LLM call、tool call 作为叶节点）

  三层对象：

  Source Tree (原生轨迹)
      ↓ 递归标注
  Semantic Annotations (语义区间 + 名字)
      ↓ 组合 + 折叠
  pprof Profile (标准火焰图输出)

  Operation Stack 公式：
  σ(n) = ⟨agent:g(n)⟩ ∥ A(n) ∥ E(n)
  - g(n) = agent 身份
  - A(n) = 语义操作路径（递归标注）
  - E(n) = evidence 叶节点（LLM call, tool call）
  - raw session/prompt ID 作为 label（供 drilldown），不作为可见
  frame（否则会打碎聚合）

  Annotation 算法（Automatic Agent Backend）

  二元递归策略：
  1. 对每个区间，backend 只看 source-visible turn summary + 当前 ancestor path
  2. 输出 STOP 或 SPLIT(非首turn, 左名, 右名)
  3. 名字匹配当前 frame → stay；匹配 ancestor → pop；新名字 → push
  4. 非空子区间独立递归；one-turn 或两侧解析成同一路径时终止
  5. 没有深度上限、叶子数阈值、或 score-tuned contraction

  名称规范化：
  - 5,537 个开放词汇名 → 1,434 个 action-first 二到三词 canonical ID
  - boundary-safe refinement：若相邻路径会变成相同，保留最少 source 区分词
  - 相同 canonical 名在跨 session 共享稳定 ID

  Non-LLM Recurrence Backend（无标签基线）

  用 NPMI (Normalized Pointwise Mutual Information) 评分相邻 action 转移：
  NPMI(a,b) = ln[p(a,b)/(p_L(a)·p_R(b))] / -ln p(a,b)
  然后用 occurrence-weighted k-means (k=2) 选全局阈值决定边界。

❯  semantic prefix 是啥?                                                        

● Semantic prefix 指的是 operation stack 里语义操作那一段。

  完整 stack 结构

  agent → [semantic operations] → [evidence leaves]
          ↑                       ↑
          这是 prefix             这是 suffix

  具体来说：

  ┌──────────────┬────────────────────────────────────────┬─────────────────┐
  │     部分     │                  内容                  │      来源       │
  ├──────────────┼────────────────────────────────────────┼─────────────────┤
  │ Semantic     │ diagnose authentication → verify       │ Agent           │
  │ prefix       │ hostname → test PAM                    │ 标注生成的      │
  ├──────────────┼────────────────────────────────────────┼─────────────────┤
  │ Evidence     │ LLM call → tool call                   │ 原生轨迹里就有  │
  │ suffix       │                                        │                 │
  └──────────────┴────────────────────────────────────────┴─────────────────┘

  RQ2 对比的两个 prefix

  ┌─────────────────────┬──────────────────────────────────┬──────────┐
  │        条件         │           Prefix 内容            │ Evidence │
  ├─────────────────────┼──────────────────────────────────┼──────────┤
  │ Direct+AgentProf    │ 语义名字（Agent 生成）           │ 相同     │
  ├─────────────────────┼──────────────────────────────────┼──────────┤
  │ Direct+Raw+Evidence │ 原生 action 字段（如 run, edit） │ 相同     │
  └─────────────────────┴──────────────────────────────────┴──────────┘

  两者的 evidence suffix 完全一样，只有 prefix 不同。

  结论的意思

  "Semantic prefix 没有额外优势" = 用 Agent 费力气生成的语义名字（diagnose SSH 
  access），和直接用轨迹里原本的 action
  字段（run），在排序问题位置这件事上效果一样。

  排序收益来自 evidence aggregation，不来自语义命名本身。

❯ 但 semantic operation path 和 raw action path 效果一样 为啥会这样?            

● 这是个好问题。原因是 semantic naming 和 problem detection 是两件不同的事。

  RQ2 测的是什么

  ▎ 把有问题的 operation 排到前面

  关键词：排序 / 检测

  Semantic prefix 提供的是什么

  diagnose authentication → verify hostname → test PAM

  这告诉你这是什么责任，不告诉你这个责任有没有出错。

  真正有区分力的是什么

  Evidence 内容：
  - LLM call 的输出写了什么
  - Tool call 返回了什么
  - 错误信息、异常状态

  tool_call: ssh git@localhost → "Permission denied (publickey)"

  这个 evidence 才包含"出错了"的信号。

  所以为什么效果一样

  ┌──────────────┬─────────────────────┬───────────────────────────┐
  │              │   Semantic prefix   │     Raw action prefix     │
  ├──────────────┼─────────────────────┼───────────────────────────┤
  │ 例子         │ diagnose SSH access │ run                       │
  ├──────────────┼─────────────────────┼───────────────────────────┤
  │ Evidence     │ Permission denied   │ Permission denied（一样） │
  ├──────────────┼─────────────────────┼───────────────────────────┤
  │ 能检测问题？ │ 靠 evidence         │ 靠 evidence               │
  └──────────────┴─────────────────────┴───────────────────────────┘

  两个条件的 evidence 完全相同，而问题检测靠的是 evidence 不是 prefix。Prefix
  只是一个"标签"，标签叫什么名字不影响它覆盖的 evidence 内容。

  Semantic prefix 真正的价值

  不是 problem detection，而是：

  1. 跨 session 聚合 — 三次执行的 SSH 问题折叠到一起看
  2. 人类可读 — diagnose authentication 比 run 容易理解
  3. Focus query — 用 pprof 的 focus 直接选中某个责任路径

  这些是 RQ1（attribution / 归因）的价值，不是 RQ2（localization /
  排序）的价值。

❯  TraceElephant MAP 这个是啥?                                                  
● 拆开讲：

  TraceElephant 是什么

  一个公开的 agent 轨迹错误定位 benchmark。它收集了 220 条真实的多 agent
  执行轨迹（GAIA、AssistantBench 等任务，由 Captain-Agent、Magentic
  等框架跑出来的，都是失败的执行），每条轨迹由人工标注了：

  - mistake_step：这条轨迹在哪一步犯了决定性错误
  - mistake_agent：哪个 agent 该负责

  也就是 ground truth 是"这条轨迹的第 5 步是罪魁祸首"这种标注。

  任务是什么

  给你一条失败轨迹（不给标注），要求你把所有步骤按"最可能是错误根源"排序。排得越
  靠前越好——开发者从上往下检查，希望第一个看的就是真正出错的那步。

  MAP 是什么

  Mean Average Precision，信息检索的标准排序指标：

  - 每条轨迹算一个 AP (Average Precision)：目标步骤在你的排序里排第 1 → AP =
  1.0；排第 2 → AP = 0.5；排第 5 → AP = 0.2（单目标时 AP ≈ 1/排名）
  - MAP = 220 条轨迹的 AP 取平均

  所以：

  ┌──────────────────────┬───────┬─────────────────────────────────┐
  │         方法         │  MAP  │            直观含义             │
  ├──────────────────────┼───────┼─────────────────────────────────┤
  │ Direct reader (grok) │ 0.502 │ 真正的错误步平均排在第 2 名左右 │
  ├──────────────────────┼───────┼─────────────────────────────────┤
  │ Direct+AgentProf     │ 0.326 │ 平均排在第 3 名左右             │
  ├──────────────────────┼───────┼─────────────────────────────────┤
  │ Direct-only          │ 0.209 │ 平均排在第 5 名左右             │
  └──────────────────────┴───────┴─────────────────────────────────┘

  在论文里的位置

  TraceElephant 是 RQ2（"profiler 输出是否对应真实问题"）三个 workload
  之一，另外两个是 AgentProcessBench（614 条）和 HINTBench（400 条）。RQ2 表格里
  TraceElephant 那一行就是 .326 / .324 / .209 那组数。

  昨晚 grok 跑的实验就是在这 220 条轨迹上加了一个新条件：不用任何
  profile，让一个强 LLM 直接读整条轨迹然后排序——结果
  0.502，比现有所有条件都高。这就是我说需要你决定怎么处理的那个结果。

❯ 我们到底在判断什么? 我们的判断方案 Direct+AgentProf  试验方案是不是有问题?    

● 问到点子上了。拆开看 Direct+AgentProf 到底在判断什么，就能看到设计的问题。

  现在的判断方案实际在测什么

  排序 = 字典序 (direct diagnostic, profile group score)

  - direct diagnostic = benchmark 自带的 judge/localizer（gpt-4o
  时代的模型，预测是冻结发布的）给每步打的分
  - profile group score = 把这个 localizer 的预测按 operation group
  跨轨迹聚合（Wilson lower bound），同组的步骤共享分数
  - 字典序意味着：profile 只能在 direct 打平的地方打破并列，永远不能推翻 direct 
  的严格排序

  所以它真正判断的是一个很窄的问题："在一个冻结的旧 diagnostic 
  之上，跨轨迹聚合能不能补一点排序信息"。答案是能（+.031/.107/.117）。

  设计的三个真实问题

  1. Tie-break-only 把上限焊死了
  Direct 排错了的地方，profile 无权纠正。所以这个设计从结构上就测不出 profile
  的独立定位能力——它只测"补充值"。AgentProf-only 那列（TraceElephant .259 >
  Direct-only .209）反而说明 profile 单独用比旧 localizer
  强，但论文没把这当主结果。

  2. 锚点太弱
  "Direct" 不是 current practice 的最强水平。grok
  实验证明了这一点：现代强模型直接读轨迹拿
  0.502，整个表格里所有条件都在它下面。我们一直在跟一个弱锚点比增量。

  3. 半循环的信号来源
  HINT/TE 的 profile group score 聚合的是同一个 localizer 自己的预测。所以
  "+.107" 的含义其实是"把同一个弱预测器的输出按组 pooling
  会变好"——这不算标签泄漏，但它测的是 pooling 效应，不是 profile
  对问题的独立对应。这也解释了为什么 raw-action 分组打平：pooling
  效应对分组语义不敏感。

  更深层的错位

  Per-trajectory"这条轨迹哪步错了"本来就是 debugging 任务。用 profiling 工具去打
  debugging 的比赛，赢了也不说明 profiling 的价值，输了还伤 thesis。RQ2
  里真正对味的其实是 AgentReward differential case（population 级：recovery
  聚集在失败侧，对应独立专家 looping 标注 AP .634）——那才是"profiler
  输出对应真实问题"的正确打开方式。

  我建议的修正实验（可以直接派给 grok）

  测互补性而不是对抗性：

  ┌──────────────────────────────┬──────────────────────────────────────────┐
  │             条件             │              Reader 读什么               │
  ├──────────────────────────────┼──────────────────────────────────────────┤
  │ Reader + raw                 │ 整条轨迹 44.6K 字符，29.9s               │
  │ trace（已跑，0.502）         │                                          │
  ├──────────────────────────────┼──────────────────────────────────────────┤
  │ Reader + profile（新）       │ 聚合 profile + 只下钻被 implicate 的     │
  │                              │ operation 的 evidence                    │
  └──────────────────────────────┴──────────────────────────────────────────┘

  如果 Reader + profile 用明显更少的输入（比如 1/3 的字符）达到接近或更高的 
  MAP，那 claim 就变成："profile 是强 reader
  的索引，让诊断更便宜/更快"——这是正面的、可量化的、和 thesis（profiling 补充
  debugging）完全对齐的结果，而且三个 workload 都能跑。

  第一步：论文要解决什么问题

  想象你的团队跑了几百次 AI agent 任务，攒下几百条执行记录。现在你想知道：

  - "这几百次运行里，钱（token）都花到哪去了？"
  - "失败的运行，都是在干什么的时候失败的？"

  现有工具（debugging/tracing）只能一条一条看：打开一条记录，从头读到尾，搞明白
  这一次发生了什么。这就像修车——一次修一辆。

  论文的主张（thesis）：光会修车不够，你还需要"车队统计报表"——这就是
  profiling。传统软件早就有这种报表（火焰图），但 agent
  没有。为什么没有？因为传统火焰图靠函数名聚合（malloc 在哪都叫 malloc），而
  agent
  的行为是自然语言描述的，同一件事每次说法都不一样，没有统一的名字就没法聚合。

  论文的方案：让一个 AI 标注员读完记录，给每段行为起统一的短名字（比如 diagnose 
  SSH access），组成层次结构，然后就能用现成的火焰图工具做报表了。

  第二步：四个实验分别在验证什么

  RQ1：这个报表真的能算清账吗？

  具体例子：三次独立运行都在做同一个"部署 Git 服务器"的任务。

  - 如果按操作次数算账：SSH 诊断只占 21% —— 看起来不是大头
  - 如果按token 算账：SSH 诊断占 46% —— 是最大的开销！

  也就是说，你用哪种度量算账，会改变你认为"瓶颈在哪"。而且点开这个 46%
  一看：三次运行都在反复诊断 SSH，最后都没修好。这是很有价值的工程发现——"我们一
  半的钱花在一个从没成功过的事情上"。

  对照实验：同样的数据，如果不用语义名字组织，会怎样？
  - 用原始结构组织：这些 SSH 工作散落在 105 
  个不同的调用里，你根本看不出它们是同一件事
  - 用粗分类（如 run 命令）组织：SSH 工作和 97 个无关操作混在一个桶里

  只有语义命名能把"三次运行里的同一件事"聚到一起。这就是 RQ1 证明的事。

  RQ2：报表能帮你找到问题吗？

  用三个公开测试集（别人标好了"这条记录哪一步出错"），看我们的报表能不能把出错的
  步骤排到前面。

  结果一：在已有的自动诊断分数上叠加我们的报表分组，排序质量在三个测试集上都提升
  了。✅

  结果二（今晚的新实验）：更有意思的玩法——让一个强
  AI（reader）来当"排查工程师"：

  ┌────────────────────────────────────┬────────────────┬────────────────┐
  │              给它什么              │ 找错质量 (MAP) │ 它读了多少内容 │
  ├────────────────────────────────────┼────────────────┼────────────────┤
  │ 什么都不给（只用旧诊断）           │ 0.209          │ —              │
  ├────────────────────────────────────┼────────────────┼────────────────┤
  │ 整条记录让它通读                   │ 0.502          │ 100%           │
  ├────────────────────────────────────┼────────────────┼────────────────┤
  │ 只给报表骨架，让它自己选要看哪几块 │ 0.455          │ 53%            │
  └────────────────────────────────────┴────────────────┴────────────────┘

  翻译：只看报表上的名字（一个字的原始内容都没看），AI 
  就能猜对"问题大概在哪块"，然后只翻开一半的内容，就拿到了通读 91% 的效果。

  再做一个对照：把报表上的语义名字换成原始命令名（run、click 这种），AI
  也能干活，但要多翻 12 
  个百分点的内容才达到同样效果。说明语义名字确实有导航价值。

  还有一个杀手锏论证：Git 那个任务群有 456 万 token，任何 AI
  的上下文窗口都装不下，"通读"根本不可能——这时候"看报表选重点"是唯一可行的方式。

  RQ3：AI 标注员起的名字靠谱吗？

  拿 405 条人类已经分好段的记录，让 AI 标注员盲标，然后对答案：

  - AI 标注和人类分段的吻合度（B³ F1）= 0.704
  - 不用 AI、纯统计规则 = 0.663
  - 直接用原始命令名分组 = 0.541

  AI 标注最好，但也不是完美——"精确切在哪一步换任务"这件事还比较难（40%
  准确率）。

  RQ4：做一份报表要花多少钱？

  - AI 标注 440 条记录：59 分钟、1200 万 token（一次性成本）

❯ 有对于好的和坏的对照的实验吗                                                  

● 有——这正是论文的 Case Study 2（差分 profiling），整个实验就是"好运行 vs
  坏运行"的对照。详细讲：

  实验设计：成功/失败配对相减

  数据：AgentRewardBench 的 440 条真实 web-agent 记录，覆盖 125 个任务。关键筛选
  条件：每个任务都同时有成功的运行和失败的运行——这样才能配对。总共配出 338 
  对"坏-好"（同一个任务，一次失败 + 一次成功）。

  防作弊设计：AI
  标注员在标注时看不到哪条成功哪条失败（outcome-blind）。先盲标完全部 7,229
  个操作，冻结，然后才打开成败标签做对比。这保证了"失败侧看到的模式"不是标注员看
  着答案编出来的。

  核心操作：把 338 个失败运行折进一张火焰图，338
  个成功运行折进同一张图的负侧，做成一张带符号的差分火焰图（bad minus
  good）——图上每块的宽度 = 失败侧比成功侧多出来的量。这张图用标准 pprof
  工具就能打开。

  看到了什么

  ┌──────────────────────────────────────────────────┬──────────┬──────────┐
  │                     行为类型                     │ 占失败侧 │ 占成功侧 │
  ├──────────────────────────────────────────────────┼──────────┼──────────┤
  │ Recovery（恢复类：重试、反复搜索、误导航后折返） │ 44.6%    │ 12.0%    │
  ├──────────────────────────────────────────────────┼──────────┼──────────┤
  │ Completion（收尾类：报告完成）                   │ 1.8%     │ 5.1%     │
  └──────────────────────────────────────────────────┴──────────┴──────────┘

  翻译成人话：失败的运行几乎一半时间在"打转"——验证码卡住反复试、搜了又搜、点错了
  退回来再点、对着同一条记录反复重试；而成功的运行很快进入正题并干净收尾。

  而且因为是递归层次结构，你可以在图里往下钻：recover interaction
  下面分出验证挑战、重复搜索、误导航、商品记录重试、仓库反复检查这些子类，每一条
  都能下钻到具体是哪条 session 的哪次调用贡献的。

  怎么证明这不是错觉

  光说"失败的图上 recovery
  块更宽"不够——万一只是失败的运行步数多呢？所以做了独立验证：

  - 有 435 条轨迹被独立的人类专家标注过"是否存在 looping（原地打转）"
  - 我们给每条轨迹算一个"recovery 暴露度"（路径含 recovery 责任的操作占比）
  - 用这个分数去预测专家的 looping 标签：AP = 0.634，而瞎猜的基线是
  0.398，提升区间 [0.181, 0.293] 完全为正

  也就是说：火焰图上看到的"打转"结构，和人类专家独立认定的"打转"高度对应——图不是
  在自说自话。

  这个实验在故事里的位置

  它回答的是 RQ2 里"规模化"的那一半：单条记录的问题定位有 benchmark
  实验，而这个实验证明在几百条记录的集合层面，target-blind 的 profile
  能把"失败运行的系统性特征"直接呈现在一张标准火焰图上，且这个特征对应真实问题。
  论文里配了两张差分火焰图（recovery 的失败侧超量 + completion
  的成功侧超量），也明确声明了边界：这是聚合诊断差异，不是因果结论（不能说
  recovery 导致失败，只能说失败和 recovery 高度共现）。

  这也是你很早就定下的要求之一："差分火焰图既要有真实 good/bad trace 的详细 case
  study，也要在真实 benchmark 上完成大范围评测"——338 对就是那个大范围评测。

❯ 算法是啥                                                                      
● AgentPProf 的核心算法

  分四层讲：输入是什么 → 怎么切分 → 怎么统一名字 → 怎么变成火焰图。

  第 0 层：输入（source tree）

  从 agent 的本地记录（Codex/Claude 的 session
  文件）重建一棵原始树，原样保留，永不改写：

  session S1
  ├── prompt P1
  │   ├── LLM call C1 (tokens=1240)
  │   │   └── tool call T1 (view file)
  │   └── LLM call C2 (tokens=830)
  │       └── tool call T2 (run test)
  └── prompt P2
      └── ...

  每个节点带着可加度量（token 数、次数、时间）。

  第 1 层：核心算法——递归找转换点并切分

  这就是你当时定的那个直觉，算法就是它的形式化：

  ▎ Agent 阅读区间 → 找到状态转换点 → 在那里切一刀 → 给两边命名 → 对每边递归 → 
  ▎ 直到没有值得切的点

  具体每一步（对一个区间）：

  1. Agent 收到：这个区间内所有 turn 的可见摘要 + 当前所在的祖先路径（比如已经在
  deploy git server 下面）
  2. 它输出二选一：
    - STOP——这个区间就是一件事，不切
    - SPLIT(第 k 个 turn, 左名字, 右名字)——第 k 个 turn
  是转换点，之前是"左名字"那件事，之后是"右名字"那件事
  3. 名字怎么解析到栈上：
    - 名字 = 当前栈顶 → stay（还是同一件事，继续）
    - 名字 = 某个祖先 → pop（回到了上层任务，比如修完岔路回主线）
    - 新名字 → push（进入新的子任务）
  4. 切出来的两半各自独立递归，各自决定继续切还是停

  终止条件：区间只剩一个 turn、Agent 说 STOP、或者切完两边解析成同一路径（说明这
  刀白切）。没有深度上限、没有叶子数目标、没有任何调出来的阈值——深度完全由内容决
  定，所以火焰图是参差不齐的（这也是你要求的）。

  跑出来的效果，比如 Git 那个案例：

  deploy git server           ← session 级
  └── diagnose SSH access     ← Agent 切出来的
      ├── verify hostname
      ├── test PAM config
      └── create fresh user
          └── LLM call → tool call   ← 原始证据保留为叶子

  第 2 层：名字统一（跨 session 聚合的关键）

  405 条轨迹各自标完后有 5,537 个自由发挥的名字（"fix the failing test" /
  "repair test failure"……）。一个只看 source、不看答案的规则把它们规范化成 1,434
  个"动词+宾语"式的 2-3 词标准名。安全阀：如果规范化会让两个相邻的不同操作变成
  同名（边界被吃掉），就保留最少的区分词；实在区分不了就拒绝合并。非相邻、跨
  session 的同名故意合并——这正是聚合的目的。

  第 3 层：折叠成火焰图（纯机械，无 AI）

  每个原始节点的栈 = agent → 语义路径 → LLM call → tool call，session/prompt ID
  降级为标签（可下钻查证，但不当作可见层——否则每条 session
  自成一列，永远聚不起来）。相同栈路径合并、宽度累加所选度量。换度量（次数→token
  →时间）不重新标注，只改宽度，1 秒重放。输出就一个标准 pprof 文件，用 go tool 
  pprof 直接看。

  备选算法（证明不依赖某家大模型）

  - Recurrence（无 LLM）：统计"哪两种相邻动作经常连着出现"（NPMI
  分数），经常连着的算同一件事，不常见的转移处切一刀；阈值用 k-means
  自动定。质量 B³ 0.663，比 Agent 的 0.704 低，但零成本
  - 同一套 annotation 接口还接了监督分类器、TF-IDF 聚类等——backend 
  可插拔是系统卖点之一

  一句话总结：算法 = 你说的那个"递归找转换点切分命名"，加上一个防碎片的名字统一
  层，落到一个纯机械的折叠器上。 AI
  只负责"切在哪、叫什么"，账本（度量守恒）由确定性代码保证。
